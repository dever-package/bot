# Agent Chat 多会话并发与运行恢复设计

状态：已确认方案 A，待实现
日期：2026-07-11

## 目标

智能体聊天按会话管理运行状态，而不是使用页面级全局 `running`：

- 同一个会话同一时间最多运行一个任务。
- 不同会话可以同时运行。
- 运行期间可以切换会话、创建新会话并在其他会话发送消息。
- 切换会话、关闭运行弹窗或刷新页面都不取消后台任务。
- 只有用户点击当前会话的停止按钮才取消任务。
- 再次进入正在运行的会话时恢复流式内容；任务已经结束时直接恢复最终结果。

## 现状问题

当前前端只有一组全局状态：`running`、`requestIDRef`、`abortRef` 和 `runTokenRef`。因此：

- `running` 会禁用所有会话按钮。
- 切换会话无法区分哪个会话正在运行。
- 关闭弹窗会执行 `abort + stop`，把界面关闭错误地等同于取消任务。
- 刷新页面后没有持久化的执行中助手消息，聊天会话无法通过 `request_id` 找回对应 run。
- `bot_agent_run` 虽然会由后台收集器完成，但最终输出不会独立写回聊天消息。

## 复用现有数据

不新增表和字段：

- `bot_assistant_message.request_id` 关联一次 agent run。
- `bot_assistant_message.status=3` 表示助手消息执行中。
- `bot_agent_run.request_id/status/output/error` 保存运行状态和最终结果。
- 现有运行流按 `request_id` 保存，默认 TTL 为 24 小时。

`request_id` 是聊天消息、运行记录和流数据之间的唯一关联键。

## 职责边界

### 后端 runtime

`service/agent/runtime.ChatService` 负责一次聊天运行的完整生命周期：

1. 校验会话、智能体、LLM 能力和输入。
2. 生成 `request_id`。
3. 保存用户消息和 `status=3` 的助手占位消息。
4. 创建 agent run 和 input step。
5. 启动 LLM 流式任务并立即返回 `request_id`。
6. 后台收集器持续消费同一条流，不依赖浏览器连接。
7. 成功、失败或取消后更新 run/step，并通过 `request_id` 更新同一条助手消息。

这属于 runtime 聊天入口的真实业务编排。前端不再分别调用消息接口保存本轮用户消息和最终助手消息。

### Assistant service

`service/assistant` 提供聚焦的内部方法：

- 开始一轮：在同一事务中插入用户消息和执行中助手消息，确保顺序稳定。
- 完成一轮：按 `request_id` 更新已有助手消息，不重复插入，也不重复增加 `message_count`。
- 校验会话归属、`agent_key` 和 `context_key`。

普通历史加载继续使用现有 assistant session API。

### 前端

前端只负责：

- 乐观展示本轮用户消息和助手等待动画。
- 按 `session_id` 保存当前运行句柄。
- 消费流并更新当前可见会话。
- 切换到其他会话时保留原任务监听。
- 页面重新加载后，根据执行中消息的 `request_id` 恢复监听。
- 用户明确点击停止时调用 stop API。

## 后端接口

### 启动运行

`POST /bot/admin/agent_runtime/run`

请求增加：

```json
{
  "session_id": 123,
  "agent": "default-agent",
  "input": "用户输入",
  "history": []
}
```

响应继续返回现有流协议，并包含 `request_id`。消息持久化由此接口内部完成。

### 查询状态

新增 `GET /bot/admin/agent_runtime/status?request_id=...`。

返回：

```json
{
  "run": {
    "request_id": "...",
    "status": "running",
    "output": { "text": "" },
    "error": ""
  }
}
```

状态只使用 `running`、`success`、`fail`、`canceled`。接口不创建新运行，不修改消息。

### 读取和停止

继续复用：

- `GET /bot/admin/agent_runtime/stream`
- `POST /bot/admin/agent_runtime/stop`

停止接口只由明确的停止按钮触发。

## 前端运行状态

用按会话索引的运行集合替换全局运行状态：

```ts
type SessionRun = {
  sessionID: number
  requestID: string
  controller: AbortController
  text: string
  lastStreamID: string
  stopping: boolean
  detached: boolean
}
```

- `Map<sessionID, SessionRun>` 保存活动任务。
- 同一会话存在活动任务时禁用该会话的发送按钮。
- 其他会话的发送按钮保持可用。
- 当前会话存在活动任务时 composer 显示停止按钮，否则显示发送按钮。
- 左侧运行中的会话显示轻量加载标记，但会话按钮仍可点击。

运行句柄和 React 展示状态分离：句柄保存在 ref，界面只保存运行会话 ID、停止状态等可渲染快照，避免异步闭包覆盖当前会话消息。

## 发送流程

1. 前端立即追加用户消息和空的运行中助手消息。
2. 调用 runtime run，携带当前 `session_id`。
3. 后端落两条聊天消息、run 和 input step，然后返回 `request_id`。
4. 前端把本地助手消息绑定到 `request_id` 并开始消费流。
5. delta 只更新对应会话；会话不在当前界面时不修改当前消息列表。
6. 后端后台收集器独立完成 run 和助手消息持久化。
7. 当前会话仍可见时，前端同时完成最终展示；不可见时，下次打开直接从数据库读取最终消息。

后端启动失败时，将本地助手占位更新为错误信息；如果运行记录已经创建，后台仍负责把错误写入持久化消息。

## 切换会话

- 移除会话按钮和新会话按钮上的全局 `running` 禁用条件。
- 切换只加载目标会话最新消息，不停止任何任务。
- 后台 delta 使用自己的 `sessionID/requestID` 定位，禁止写入当前显示的其他会话。
- 切回运行会话时，优先复用内存中的运行句柄；如果没有句柄，则进入恢复流程。

## 关闭弹窗和页面卸载

### 关闭弹窗

- 不调用 stop。
- 组件仍挂载时继续监听并让后端正常完成。
- 再次打开时重新加载会话；活动运行句柄继续复用。

### 刷新、路由离开或组件卸载

- 只 abort 本地网络监听，释放浏览器资源。
- `stopOnAbort=false`，不调用 stop API。
- 将本地任务标记为 detached，不把它保存为失败或取消。
- 后台 runtime 和收集器继续执行并更新数据库。

## 恢复流程

加载会话时检查 `status=3` 且有 `request_id` 的助手消息：

1. 请求 runtime status。
2. `success/fail/canceled`：使用 run 的最终数据更新界面；后端正常情况下已经更新同一条消息。
3. `running`：从现有 stream 按 `request_id` 重新订阅；刷新后从 `0-0` 重放并重建当前文本。
4. 流读取失败时再次查询 status；已完成则使用 run output，仍运行则显示可重试状态。
5. run 不存在或执行中状态超过有效期时，将占位消息改为明确的中断错误，避免永久显示三点动画。

流 TTL 到期后不依赖流恢复历史文本；已完成 run 的最终 `output` 永久保存在数据库中。

## 停止流程

- 停止按钮只作用于当前会话的 `request_id`。
- stop 成功后等待或读取取消结果，移除该会话的活动运行句柄。
- 已生成文本存在时保留部分文本；没有文本时显示“已停止生成”。
- 取消不会影响其他会话的任务。

## 并发约束

- 同一会话：最多一个运行任务，保证上下文顺序确定。
- 不同会话：允许并行，互不共享 controller、request ID、文本缓冲和停止状态。
- 后端以会话中的执行中助手消息作为同会话运行锁；重复启动返回明确错误。
- 前端通过运行集合防止普通重复点击，后端约束负责多标签页等并发情况。

## 错误处理

- 消息持久化失败：不启动运行，前端撤销等待态并显示错误。
- run 创建或能力启动失败：后端把助手占位更新为失败。
- 前端流断线：自动重连；不能重连时查询 status。
- 后端运行成功但前端已离开：后台收集器更新助手消息，重新进入即可看到结果。
- 后端进程异常退出遗留 `running`：恢复时根据 run 状态和超时规则标记中断。

## 不在本次范围

- 不增加工具调用或 agent loop。
- 不修改知识库、技能、team 或 flow。
- 不增加数据库表或字段。
- 不迁移旧 `show-agent` 的复杂结果卡片、交互面板和附件能力。
- 不允许同一会话内并行发送多轮。

## 验收标准

1. 会话 A 生成时可以切换到会话 B，并在 B 发起另一项生成。
2. A、B 的 delta、停止按钮和最终结果不会串到对方会话。
3. 切换回 A 时可以看到已有流式文本并继续接收。
4. 关闭弹窗后任务继续；再次打开能看到运行态或最终结果。
5. 刷新页面后，执行中的消息通过 `request_id` 恢复；已完成消息直接展示最终结果。
6. 只有停止按钮会取消任务，切换、关闭和卸载不调用 stop API。
7. 同一会话不能同时启动两次，不同会话可以并发。
8. 执行中助手消息最终原地更新，不产生重复助手消息，不重复增加消息数量。
9. 左侧运行会话有状态提示但始终可以点击。
10. 现有会话和消息游标分页、三点等待、Markdown 流式展示继续工作。

按项目要求不运行 build、test、lint 或浏览器自动化测试；实现后只执行格式化、源码静态检查和 Dever audit，由用户手动验收界面与并发行为。
